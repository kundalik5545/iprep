# iPrep Progress Report

> Date: 2026-05-06
> Scope: High-level product and architecture progress based on the docs and current repo structure.

---

## Current Snapshot

iPrep is in the local-first MVP foundation stage. The repository has moved beyond planning into a TypeScript monorepo scaffold with separate apps for frontend, server, and CLI, plus shared packages for common schemas, database access, LLM adapters, and provider integrations.

The architecture direction is settled: Vite + React for the browser app, Express + WebSocket for local orchestration, Prisma + SQLite for local persistence, and a provider abstraction for voice, STT, TTS, and LLM analysis. The planned cloud path remains compatible with the current local-first shape.

## Completed or Mostly Established

- Monorepo structure is in place with `apps/frontend`, `apps/server`, `apps/cli`, and `packages/*`.
- Root workspace configuration exists through `package.json`, `pnpm-workspace.yaml`, shared TypeScript config, Prettier, and ESLint setup.
- `@iprep/shared` has the strongest implementation state so far:
  - Zod schemas for sessions, analysis, providers, and environment config.
  - Shared TypeScript types.
  - Core constants for app identity, ports, interview packages, tutors, modes, statuses, and provider slugs.
  - Utility formatting helpers.
- Architecture and implementation plan documents are written and cover:
  - Local-first to cloud migration strategy.
  - Provider-agnostic adapter design.
  - CLI-first local workflow.
  - Database model plan.
  - Frontend, backend, and analysis flows.
- Package and app folder structures are present across the main planned layers.

## Scaffolded but Still Pending Core Logic

- `packages/llm/adapter-utils` exists, but core process spawning, stream parsing, session management, and error handling still need implementation.
- CLI adapters for Claude, Gemini, and Codex are scaffolded, but provider-specific spawning, parsing, prompt building, and session continuity still need working code.
- `packages/llm/providers` has provider files for Deepgram, OpenAI, Claude, Gemini, Codex, and Ollama, but the registry and provider implementations are still largely placeholders.
- `packages/db` has the intended query layout and Prisma location, but the Prisma schema and query functions still need to be built.
- `apps/server` has the expected route, service, WebSocket, and utility layout, but Express app wiring, REST routes, WebSocket handlers, and orchestration services remain pending.
- `apps/frontend` has the expected page, component, hook, store, and lib layout, but the actual React UI and client-side flows still need implementation.
- `apps/cli` has the command layout, but user-facing commands such as `init`, `doctor`, `setup`, `status`, `start`, `sessions`, `analyze`, `export`, and `keys` still need logic.

## Product Direction Confirmed

- Phase 1 focuses on a local-first MVP with low operating cost and BYOK provider support.
- The app should keep provider secrets server-side or local-side, not in the browser.
- Analysis should use the cheapest available provider first, then fall back through CLI and paid API providers.
- Shared Zod schemas are the contract between frontend and backend.
- The local data model should be designed for SQLite first, with a future Postgres cloud path.
- The system should remain provider-agnostic so Deepgram, OpenAI, Gemini, Claude, Codex, and Ollama can be swapped or combined through adapters.

## Main Risks and Gaps

- The plan and architecture docs are ahead of the executable implementation.
- Several docs still describe packages as "structure done", while the repo now has more package files than the older status tables reflect.
- Provider architecture is central to the product, but the registry and concrete provider behavior are not yet working.
- Database persistence is not ready until Prisma schema, migrations, and query functions are implemented.
- End-to-end interview flow is not yet available because backend orchestration and frontend UI are still placeholders.
- Build and runtime verification still need to be completed after dependency installation and package implementation.

## Overall Status

The project is currently in an architecture-complete, scaffold-heavy state. The next meaningful milestone is to convert the scaffold into one thin working vertical slice:

`CLI/server starts -> package and tutor data loads -> session starts -> transcript is accepted -> analysis runs through one provider -> result is stored and returned.`

Once that slice works, frontend implementation and additional provider support can be added with much lower uncertainty.
